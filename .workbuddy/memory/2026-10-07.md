# 2026-10-07 工作日志

## 日志分析小工具（log_analyzer）
- 需求：Python 读取日志文件、统计 ERROR 出现次数。
- 产出文件：
  - `log_analyzer.py` — 单文件 CLI 工具，零第三方依赖（仅标准库 argparse/re/io/json/collections）。
  - `sample.log` — 32 行混合级别样例日志（INFO/WARN/DEBUG/ERROR/FATAL），用于演示与自测。
- 关键设计决策：
  - 流式逐行读取（`io.TextIOWrapper` 包 `BufferedReader`），先探测前 64KB 判断编码
    （utf-8-sig → utf-8 → gbk → latin-1），GB 级日志内存占用恒定。
  - 日志级别用带前后边界断言的正则匹配，避免把 `error_code` 这类字段误判为级别。
  - 错误模版归一化（时间戳→`<TS>`、16 进制 ID→`<HEX>`、IP→`<IP>`、数字→`<N>`）后再聚类，
    否则每行都因 orderId/traceId 不同而被算成独立错误，TOP N 失去意义 —— 这是本工具
    相对"直接 grep -c ERROR"的核心价值。
  - 退出码约定：0 正常 / 1 命中错误（`--fail-on-error`，用于 CI 巡检）/ 2 文件或参数错误。
- 踩坑记录：
  - 初版用 `Path.read_bytes()` 解码，与"大文件友好"矛盾，已改为流式 + 头部探测。
  - 文本输出分支最初忽略了 `--samples`，样例数量不受控，已修复。
  - 本机 Bash 工具 PATH 异常（`dirname`/`ls`/`mkdir`/`tail`/`head` 均 command not found），
    运行 Python 需用绝对路径，且不能依赖 shell 内置外的命令。

## 追加：无参数引导修复
- 用户在 PyCharm 里直接点运行，未传 logfile 参数，argparse 报英文 usage 错误。
- 已在 `main()` 增加判断：`argv is None and len(sys.argv) == 1` 时走 `no_args_hint()`，
  打印中文引导（命令行用法 + PyCharm Edit Configurations 填 Parameters 的步骤），退出码 2。
- 注意 `main(argv)` 的默认值语义：显式传 argv 列表（哪怕是空列表）仍走 argparse 正常报错，
  只有"完全没传且 sys.argv 也为空"才走引导——保证管道/CI 场景行为不变。

## 追加：v1.1.0 服务器场景支持
- 用户实际场景：CloudPivot(云枢) Java 服务，日志在
  `/data/cloudpivot/program/backEnd/webapi/logs/`，问的是"服务器上路径怎么填"。
  关键点：他给的是**目录**不是文件，所以工具必须有目录支持才有用。
- 新增能力：
  - `logfile` 改为 `nargs="+"`，支持多个文件合并统计；
  - 传目录时自动扫描，默认选"主业务日志"，`--merge` 合并全部，`--pattern` 通配符过滤；
  - `.gz` 轮转日志用 gzip 模块直接读（gzip 不可 seek，编码探测改为单独开一次读前 64KB）；
  - 多文件用 `contextlib.ExitStack` + `itertools.chain.from_iterable` 串流，
    复用原有 `analyze()` 签名不变（它只迭代行），stdin 不关闭。
- 踩坑：初版目录扫描把 JVM 的 `gc.log.0.current` 当成业务日志，且因 mtime 最新被默认选中，
  会污染统计。已加 `AUX_RE` 辅助日志黑名单（gc.log/hs_err_pid/stdout/stderr/*.current/
  *.tmp/*.lck/*.idx/*.pid）在目录扫描时跳过，并加 `pick_primary()` 优选规则：
  正在写的业务日志(webapi.log) 优先于轮转归档(webapi.log.2026-10-06)，再看 mtime。
  用户显式写出文件名时不做拦截（仍可分析 gc.log）。
- 待观察：ID 归一化对 7 位混合 ID（如 traceId=abc0def）聚类不彻底，
  因为 HEX 规则要求 8+ 位。真实 traceId 多为长 hex/uuid，暂未调整。
